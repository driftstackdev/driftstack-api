# CDN strategy — marketing site

V-221 — Cloudflare Pages caching strategy for `apps/marketing-site/`.
Cache rules live in `apps/marketing-site/public/_headers`; this doc
explains the why behind each tier so a future change doesn't accidentally
break customer page loads or starve crawlers.

## Where this applies

- **`apps/marketing-site/`** — static Astro build deployed to Cloudflare
  Pages at driftstack.dev. Output is `dist/`; `public/_headers` is copied
  verbatim during deploy and applied per-path at the edge.
- Not applicable to `apps/customer-dashboard/` (SSR, behind auth, no
  public caching) or `apps/server/` (Fastify on Hetzner; cache-control
  set per-route in code).
- Not applicable to `apps/admin-panel/` (internal-staff surface, never
  cached publicly).

## The three tiers

### Tier 1 — Hashed assets (immutable, 1 year)

```
/_astro/*       → public, max-age=31536000, immutable
/*.svg|png|...  → public, max-age=31536000, immutable
fonts (woff2)   → public, max-age=31536000, immutable
```

Astro emits hashed filenames under `/_astro/*` (CSS bundles, JS chunks).
The hash flips on every content change, so a real update produces a new
URL the browser hasn't seen — guaranteeing a fresh fetch. Between
updates, browsers and the edge cache the file forever.

`immutable` tells the browser not to revalidate even on hard reloads
(except force-refresh). Combined with the 1-year max-age this means
returning visitors fetch zero bytes for unchanged assets.

Stable-name media (logos, og-images uploaded with non-hashed names) is
treated identically. If a stable-name image needs to change, deploy with
a new filename or query string — don't try to bust the cache by waiting.

### Tier 2 — Homepage (5min browser, 1d edge, 1d SWR)

```
/, /index.html  →
  Cache-Control: public, max-age=300, s-maxage=86400, stale-while-revalidate=86400
/*  → security headers only (no Cache-Control)
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Content-Security-Policy: <audited browser-origin policy>
```

The explicit cache policy applies only to `/` and `/index.html`. Other
HTML routes use the Cloudflare zone default and every Pages deployment
purges the project edge. The `/*` rule is deliberately security-only:
Cloudflare merges every matching rule, so putting `Cache-Control` there
would override/degrade the immutable asset and crawler tiers too.

Numbers picked deliberately:

- **`max-age=300`** (5 minutes browser): a customer who lands on the
  homepage, clicks through to pricing, then comes back gets the cached
  homepage. After 5 minutes a return visit re-validates against the
  edge. Short enough that a deploy lands in front of customers within
  minutes for active users.
- **`s-maxage=86400`** (1 day edge): Cloudflare's edge keeps a hot copy
  for 24h. With ~tens of edge POPs and most traffic served from a small
  set, this gives near-100% cache-hit rate on warm POPs.
- **`stale-while-revalidate=86400`** (1 day): when the edge cached copy
  hits 24h+1s, the next request serves the stale copy AND fires an async
  revalidation. Customer never waits on a re-fetch; the next customer
  gets fresh.

The Pages deploy invalidates the project edge, so a new release does not
wait for the one-day homepage TTL. If a zone cache ever outlives a deploy
(for example after a platform incident), use the Cloudflare purge API.

The security headers live in the catch-all and merge onto every response.
That keeps one auditable policy without repeating fields in each cache
tier.

### Tier 3 — Crawler artefacts (1 hour)

```
/robots.txt          → public, max-age=3600
/sitemap-index.xml   → public, max-age=3600
/sitemap-*.xml       → public, max-age=3600
```

Googlebot et al re-check robots and sitemaps periodically. 1 hour is
the sweet spot:

- Fast enough that a fresh sitemap (new blog post, new docs page)
  propagates the same day a deploy lands.
- Slow enough that we don't burn origin requests on every crawler visit
  — at scale, a major crawler can hit `/robots.txt` thousands of times
  per day across IPs, and even a free-tier CDN doesn't want to round-
  trip every one.

Sitemap files are auto-generated by `@astrojs/sitemap` on each build
(see `astro.config.mjs`). Filename pattern `/sitemap-*.xml` covers both
the index and split files when the sitemap exceeds 50k URLs (won't
happen pre-launch but the pattern is forward-compatible).

## Match-order semantics

Cloudflare Pages applies and merges every matching rule. Ordering remains
specific-to-broad for readability, but it is not first-match-wins. This
is why the broad catch-all must never set `Cache-Control` or repeat a
security field already present in another matching block.
The current order:

1. `/_astro/*` — most specific path prefix
2. Extension-based matchers (`/*.svg`, `/*.png`, …)
3. Specific file paths (`/robots.txt`, `/sitemap-*.xml`)
4. `/` and `/index.html`
5. `/*` catch-all (last)

If a new pattern is added, place it above the catch-all and audit how its
fields merge. The `/*` catch-all MUST stay last and security-only.

## Security headers — why these three

- **`X-Frame-Options: DENY`** — prevents the site from being embedded in
  an iframe on another origin. Defense-in-depth against clickjacking;
  the marketing site has no legitimate use case for being embedded.
- **`X-Content-Type-Options: nosniff`** — disables MIME-type sniffing
  in older browsers. Prevents a `.txt` upload from being rendered as
  HTML or a `.png` from being executed as a script. Cheap to set, no
  downside.
- **`Referrer-Policy: strict-origin-when-cross-origin`** — when the
  browser follows an outbound link, the destination sees only our
  origin (`https://driftstack.dev`), not the full path. Avoids leaking
  which marketing page a customer came from to third-party analytics
  or partner pages.

`Strict-Transport-Security` and an enforced `Content-Security-Policy`
live on the `/*` catch-all so Cloudflare merges each field onto every
response exactly once. The CSP audit completed 2026-07-13: marketing
loads application code and assets only from itself, connects only to the
public API and optional Sentry ingest, forbids frames/objects/remote
scripts, and permits the intentionally inline Astro code until the static
build can emit stable per-page hashes.

## What we don't do

- **Per-page TTL overrides** — every HTML page uses the same Tier 2
  config. Special-casing creates surprise; if a page genuinely needs
  different caching it's a sign the page belongs elsewhere (dashboard,
  app, or signed URL).
- **Vary headers** — the marketing site doesn't serve content based on
  cookie, language, or device. Adding `Vary` would fragment the cache
  for no benefit.
- **CDN-level transforms** (image resize, HTML minification) — Astro
  already minifies at build; image variants are committed as separate
  files. Edge transforms add a class of mismatch bugs (origin vs edge
  output diverge) we don't need to take on.
- **Worker-based caching logic** — `_headers` is declarative and reads
  in 30 seconds. A Worker would be opaque, harder to audit, and would
  cost requests against the Workers quota for no gain.

## Verifying the rules

After a deploy:

```sh
# Hashed asset — should be max-age=31536000, immutable
curl -sI https://driftstack.dev/_astro/<hashed-bundle>.js | grep -i cache

# HTML page — should be max-age=300, s-maxage=86400, plus security headers
curl -sI https://driftstack.dev/pricing | grep -iE 'cache|frame|content-type-options|referrer'

# Crawler artefact — should be max-age=3600
curl -sI https://driftstack.dev/robots.txt | grep -i cache
```

If a header is missing, the most likely cause is rule-order regression
in `public/_headers` (a broader pattern shadowing a specific one).

## Changing the rules

`apps/marketing-site/public/_headers` is the source of truth. Edit
there, deploy, verify with the curl commands above. There is no
staging-vs-prod split for header rules — the same file ships to all
Pages deployments. If a rule change is risky, ship it on a Pages preview
branch first and test against the preview URL.
